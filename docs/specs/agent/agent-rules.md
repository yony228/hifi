# Hify Agent 协作守则

> AI Agent 在 Hify 项目中工作的默认行为规范。面向 Claude Code / AI 编程助手，确保产出可控、不越界。

---

## 一、核心原则

### 1.1 最小惊扰原则

**Agent 是协作者，不是主人。** 任何可能让人类感到意外的操作（写代码、改文件、提交、推送），必须来自人类的明确指令。宁可多问一句，也不自作主张。

### 1.2 显式授权原则

**默认不做，授权才做。** 以下操作有明确的免责边界：

| 操作类别 | 讨论中默认 | 需要用户明确说 |
|---|---|---|
| 读文件、搜索代码、分析问题 | ✅ 随时可以 | — |
| 写新文件 | ❌ 禁止自动 | "帮我创建" / "实现" / "写代码" |
| 修改现有文件 | ❌ 禁止自动 | "改一下" / "修复" / "重构" |
| 运行 `git commit` | ❌ 禁止自动 | "帮我提交" / "commit" / "提交修改" |
| 运行 `git push` | ❌ 禁止自动 | "push" / "推到远程" / "推送" |
| 运行 `mvn test` | ✅ 验证需要时 | — |
| 运行 `mvn compile` | ✅ 检查编译时 | — |

## 二、讨论 vs 实现

### 2.1 讨论模式（默认状态）

用户在聊天中描述问题、讨论方案、询问意见时，Agent 处于**讨论模式**：

- **可以：** 分析问题、给出建议、展示代码片段作为示意、解释技术选型
- **禁止：** 创建文件、修改文件、执行写操作

**触发词判定**：以下词语表示讨论，不是实现指令：

> "怎么实现" / "你觉得" / "有没有更好的" / "分析一下" / "什么是" / "为什么"

### 2.2 实现模式（授权后）

用户明确给出执行指令后，进入**实现模式**。

**触发词：** "帮我实现" / "写一下" / "改代码" / "完成 plan 第 X 项" / "修复这个 bug"

**实现模式的边界（严格）：**

```
用户实现指令
    │
    ▼
  Step 1: 写代码（遵循 docs/specs/ 下的规范）
    ↓
  Step 2: 写测试
    ↓
  Step 3: mvn test（全量，含新增 + 回归）
    ↓
  Step 4: 若关联 plan 条目 → 标记 ✅ 已完成
    ↓
  🛑 停止。向用户报告结果。
```

**实现模式不包括：**
- ❌ CR（/code-review）—— CR 是提交流程的一环，不是实现流程的一环
- ❌ git commit —— 提交是独立授权
- ❌ git push

**⚠️ 实现 ≠ 提交。** 上述触发词只授权「写代码 + 测试」，**不包括 git commit**。提交必须单独获得用户指令（见 §三）

**⚠️ 实现完毕后必须停下来。** 代码写完、测试通过之后，Agent 报告结果即可，**禁止**继续做 CR 或 commit。

**示例对照：**

| 用户说的 | 模式 | Agent 行为 |
|---|---|---|
| "这个 LLM 超时应该怎么配？" | 讨论 | 分析 + 给配置建议，**不动代码** |
| "LLM 线程池怎么设计？" | 讨论 | 讲方案，**不动代码** |
| "帮我实现 LLM 线程池配置" | 实现 | 写代码 + 测试 → 🛑 报告结果 |
| "完成 plan-bizBase §7" | 实现 | 写代码 + 测试 + 标记 plan → 🛑 报告结果 |
| "这里加个日志" | 实现 | 改代码 + 测试 → 🛑 报告结果 |
| "你觉得要不要加缓存？" | 讨论 | 给建议，**不动代码** |
| "帮我提交" | 提交 | 走 §3.2 提交流程（CR → diff → commit） |

### 2.3 模糊指令的处理

如果用户指令不够明确（如 "优化一下"、"改改"），Agent 应该**先确认再动手**：

```
用户: "优化一下这里的性能"
Agent: "当前这段代码可能的优化方向：A/B/C。你倾向哪一种？还是都要？"
```

## 三、提交规范（对齐 CI/CD 规范）

### 3.1 提交时机

| 何时可以提交 | 何时不能提交 |
|---|---|
| 用户明确说 "帮我提交" / "commit" | "完成 plan 第 X 项"（只授权实现，不含提交） |
| 用户说 "提交修改" / "提交代码" | "帮我实现 xxx"（只授权写代码，不含提交） |
| 全量测试通过 + CR 通过后 | 测试未跑或失败时 |
| 用户确认过 diff 后 | 用户还没看过变更内容 |

### 3.2 提交工作流（仅在用户明确说"提交"后启动）

**⚠️ 此工作流只在收到 "帮我提交" / "commit" / "提交" 指令后才启动。**
实现指令（"完成 plan"、"帮我实现"、"写代码" 等）**不会**触此工作流。

收到提交指令后，Agent 必须**严格按以下顺序**执行，**禁止跳过任何步骤**：

```
用户: "帮我提交"
        │
        ▼
  ┌─ Step 1: mvn test ──────────────────────────────────
  │  全项目测试，失败 → 硬阻塞，修复后重新 Step 1
  └─ 通过 ↓
  ┌─ Step 2: CR Agent（/code-review）────────────────────
  │  审查当前 diff，产出 findings 列表展示给用户
  │  用户勾选修复项 → 应用修复 → 回到 Step 1 重新测试
  │  用户全部跳过 → 继续
  │  ⚠️ 此步禁止跳过。即使 Agent 自己看过代码、认为没问题，也必须跑 CR
  └─ 完成 ↓
  ┌─ Step 3: git diff --stat ───────────────────────────
  │  向用户展示变更文件列表和行数
  └─ 完成 ↓
  ┌─ ⚠️ 等待用户提交指令 ─────────────────────────────
  │  Agent 必须停下来，明确问："需要我提交吗？"
  │  用户说"提交"/"commit"/"帮我提交" → 继续 Step 4
  │  用户说"先看看"/"等会"/其他 → 停止，不提交
  │  🚫 CR 零 findings ≠ 自动提交。即使零问题也必须等用户确认。
  └─ 用户确认 ↓
  ┌─ Step 4: git commit ────────────────────────────────
  │  遵循 Commit 格式，关联 plan 文档
  └─ 完成
```

**违规记录：**
1. 2026-08-05，item 7/8/9 + specs 重组 + 规则修复 + dev 配置补丁，共 8 个 commits 跳过 Step 2（CR）
2. 2026-08-05，item 5（SseUtil），Step 1-3 正确执行，但 **Step 3 后未等待用户确认直接 commit**。根因：将 "CR 零 findings" 等同于 "授权提交"，而实际上提交是需要独立授权的独立动作

### 3.3 默认不自动提交（最高优先级）

> **提交是独立授权项，不与任何其他操作捆绑。**

- "完成 plan 第 X 项" → 写代码 + 测试 ✅ / 提交 ❌
- "帮我实现 xxx" → 写代码 + 测试 ✅ / 提交 ❌
- "修复这个 bug" → 改代码 + 测试 ✅ / 提交 ❌
- **只有** "帮我提交" / "commit" / "提交代码" 才触发 git commit

即使连续多个任务都要求了提交（如 item 7 用户说了"帮我提交"），后续任务（item 8、9）也必须重新获得提交指令。**上一次的授权不延续到下一次。**

```
Agent: "代码完成，全部 28 个测试通过。需要我提交吗？"  ← 正确
Agent: (默默 git commit)                                ← 错误
```

## 四、代码规范遵循

### 4.1 写代码前的必读文件

写任何代码之前，Agent 必须自行查阅对应的规范文件：

| 场景 | 必读文件 |
|---|---|
| 新建模块、调整模块依赖 | `docs/specs/design/design.md` |
| 写 Java 代码 | `docs/specs/design/code-organization.md` |
| 写 LLM 调用逻辑 | `docs/specs/design/llm-invoke-spec.md` |
| 新增表/字段 | `docs/specs/design/data-model.md` |
| 写 Controller / DTO | `docs/specs/design/api-spec.md` |
| CI/CD 相关问题 | `docs/specs/agent/cicd.md` |
| 不确定 Agent 行为边界 | 本文档 |

### 4.2 代码风格

- **匹配周边代码风格** — 注释密度、命名、缩进与已有代码一致
- **使用项目工具类** — 序列化用 `JsonUtil`、分页用 `PageUtils`，不重复造轮子
- **注释面向 AI + 人** — 写清楚「为什么这么做」，不只是「做了什么」

### 4.3 测试要求

- 新组件必须有测试，无测试的代码不要合并
- 库模块（hify-common / hify-model 等）的测试不依赖 Spring 容器，纯 JUnit 可跑
- 测试按 `@Nested` 分组，AssertJ 断言，中文 `@DisplayName`

## 五、Plan 驱动开发

### 5.1 有 Plan 按 Plan 来

项目 plan 文件（`docs/plan/plan-*.md`）是开发任务的主线。Agent 执行时：

1. 先读 plan 文件，理解当前条目的要解决的问题和实现要点
2. 查阅 spec 文件中对应的技术方案
3. 完成代码 + 测试
4. 在 plan 文件中标记 `✅` 已完成

### 5.2 偏离 Plan 时的处理

如果实现过程中发现 plan 与实际情况不符：

```
Agent: "plan 里说用方案 A，但我发现因为 X 原因，方案 B 更合适。改 plan 还是按方案 B 先做？"
```

不要擅自偏离 plan 静默实现。
